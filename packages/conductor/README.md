# @fabrial/conductor

PG Conductor adapter for Fabrial's `DurableRuntime`. Registration is side-effect-free; `start()` migrates Postgres and starts workers. Handlers replay from the top after suspension. Explicit operation IDs address saved steps and waits; core supplies repeated-ID suffixes.

```ts
import { conductor } from "@fabrial/conductor";

const runtime = conductor(
	{ connectionString: process.env.DATABASE_URL! },
	{
		queue: "default",
		worker: { concurrency: 8, pollIntervalMs: 100, flushIntervalMs: 100 },
		pollIntervalMs: 250,
	},
);
// Pass runtime to fabrial({ runtime, ... }); core registers workflows and events.
```

Alternatively supply `{ sql }` with a `postgres.Sql` pool. An injected pool belongs to the caller; `stop()` does not close it. An adapter-created pool is closed on stop; create a new runtime instance to restart it. `logger` accepts Conductor's logger interface. `worker` accepts partial native `WorkerConfig`; `pollIntervalMs` separately controls fallback races and settlement reconciliation. Keep the queue's workflow catalog consistent across instances. `now()` exposes the wall clock used by core; durable wait deadlines use Postgres's clock.

Event-triggered handlers receive the **clean event payload**, matching core's `TriggerPayload` and test runtime. Cron handlers receive `{ name: scheduleName }`, with a generated interaction ID and no thread/actor. `waitForEvent`/event branches of `waitForAny` return `{ name, payload }`. Core resolves ownership before emitting: only the named workflow's matching owner triggers run; observers always run. Overlapping subscriptions on one workflow produce one invocation. An observer-only match never inherits thread ownership. `emit(..., { dispatchId })` merges triggered invocations by `(queue, dispatchId, workflow)` across event categories without merging event receipts; the first submission's input and metadata win, including after completion/restart. If one workflow is both an owner and an observer across those categories, concurrent routing does not guarantee owner precedence.

## Temporary shims

All receipts, waits, outputs, and parent links live in Conductor's tables. No Fabrial-owned tables are added. Direct SQL and private context access are confined to this package and tied to the pinned vendor revision.

### Terminal notifications

A restart-safe monitor calls `RuntimeWorkflow.onSettled` after terminal completion/failure/cancellation, never on suspension. Delivery is **at least once** (crash between the hook and receipt, or competing monitors); hooks must be idempotent. Core supplies this hook to clear thread routing state and emit `fabrial.execution.settled` with the execution ID as dedupe ID, so repeated hook deliveries still dispatch the event once. Hook failures are logged independently and retried in a cyclic scan; a poison hook does not block other executions, even beyond the first 100-row batch.

Without a hook the monitor emits settlement events for failures/cancellations that a handler wrapper cannot see (retry exhaustion, suspended cancellation). Successful notifications require the hook (core always supplies one); the no-hook fallback does not emit success events, avoiding an unbounded loop of success notifications from raw settlement observers. Reconciliation continues on a new instance with the same queue and registered catalog. Core's process-local cancellation callbacks cannot be reconstructed by this adapter after restart.

### Contract coordination

No additional port method is required for the implemented behavior. For deterministic owner precedence when one ingress spans event categories, a proposed additive change is `DurableRuntime.emit` option `dispatchOwner?: { workflow: string; event: string }`, supplied on **every** emission in that ingress. The runtime could then skip non-canonical observer submissions for the selected workflow, while preserving dedupe for all other observers. This proposal is not implemented; the coordinator must decide between canonical-owner precedence and the current first-submission-wins policy. The strict mutex and race-safe wait promises still require upstream fixes, not weaker port guarantees.

### Upstream priorities

Keep `#1`, `#2`, `#8`, and `#9` as P0. Native retained, idempotent emit receipts are also needed by the fallback race. Add claim-guarded, indexed races (`#6`) and independent start/result retrieval (`#7`) to remove polling and output-step SQL. For `#5`, preserve the reason/distinct terminal status atomically for pending and running cancellation (running settlement currently overwrites the requested reason with the claim's stale error), reduce heartbeat-bound cancellation latency, provide detached calls, and clarify whether a running step finishes and records its result before terminal settlement. Terminal hooks must be restart-safe, at-least-once, and isolate poison deliveries. For `#4`, strict per-key claims and a fencing token remain necessary; soft grouping alone cannot satisfy the port's strict mutex documentation.
